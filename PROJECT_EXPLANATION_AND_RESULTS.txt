1. DATASET EXTRACTION: HOW MANY FILES & WHAT WERE THEIR EXACT SIZES?
--------------------------------------------------------------------------------
When downloading from the UCI Machine Learning Repository (Dataset ID #280,
"HIGGS"), the upstream archive contains:
  * Raw Upstream Archive: 1 compressed file named `HIGGS.csv.gz`
    - Compressed download size : 2.62 GB (2,816,407,858 bytes)
    - Uncompressed full size   : 7.48 GB (11,000,000 rows x 29 columns)
    - Column structure         : Column 0 is the binary label (1 = Higgs Boson
      signal, 0 = background process). Columns 1 to 28 are the 28 continuous
      high-energy physics features (21 low-level detector momenta/angles +
      7 high-level invariant mass features: m_jj, m_jjj, m_lv, m_jlv, m_bb,
      m_wbb, m_wwbb).

When we extracted and cleaned the dataset using `scripts/prepare_higgs_data.py`,
we streamed the archive over HTTP, removed malformed/NaN rows, and split the
data into TWO (2) clean files inside the `data/` directory:

  1. `data/higgs_clean.csv`
     - Exact Size  : 130.81 MB (137,159,578 bytes)
     - Exact Rows  : 597,638 collision events
     - Features (d): 28 floating-point numbers per row
     - Total Values: 16,733,864 floats (597,638 x 28)
     - Purpose     : The unlabeled feature matrix fed into K-Means clustering.

  2. `data/higgs_labels.txt`
     - Exact Size  : 1.14 MB (1,195,276 bytes)
     - Exact Rows  : 597,638 binary integer labels (0 or 1)
     - Purpose     : Ground-truth labels used ONLY after clustering finishes
                     to measure how well K-Means separates real Higgs boson
                     signal events from background events.

  -> TOTAL EXTRACTED FILES IN `data/`: 2 files
  -> TOTAL COMBINED SIZE ON DISK     : 131.95 MB (138,354,854 bytes)

(Note: Because GitHub blocks files larger than 100 MB, `data/higgs_clean.csv`
is listed in `.gitignore` and can be regenerated anywhere—including on NUS
Vanda—by running `python3 scripts/prepare_higgs_data.py`.)

2. CHRONOLOGICAL EXPLANATION OF EVERYTHING WE BUILT (STEP BY STEP)
--------------------------------------------------------------------------------

STEP 1: 1-Core Serial Baseline (`src/kmeans_serial.cpp`)
  - What we did:
    Implemented Lloyd's K-Means algorithm in C++17 on a single CPU core.
    In each iteration:
      (a) Expectation step: For each of the N = 597,638 points, compute the
          squared Euclidean distance to all K centroids across d = 28 features
          and assign the point to its closest centroid.
      (b) Maximization step: Recompute each of the K centroids as the mean of
          all points assigned to it, and measure the maximum centroid shift.
  - Why we did it:
    Provides the 1-core reference runtime to calculate parallel Speedup S(P)
    and Parallel Efficiency E(P), and saves the converged centroids to
    `results/centroids_serial.txt` so we can mathematically verify that all
    parallel implementations produce the exact same clusters.

STEP 2: Pure MPI Distributed-Memory Parallelization (`src/kmeans_mpi.cpp`)
  - What we did:
    Parallelized K-Means across P separate MPI processes (ranks) using 1D
    Row-Block Domain Decomposition:
      (a) Rank 0 loads the dataset and initial centroids, broadcasts the
          initial centroids via `MPI_Bcast`, and scatters 1/P of the rows
          (N / P points) to each MPI rank using `MPI_Scatterv`.
      (b) In each iteration, every rank computes distances ONLY for its local
          N/P points and accumulates partial cluster sums (`local_sums`) and
          point counts (`local_counts`).
      (c) At the end of each iteration, all ranks synchronize via two global
          `MPI_Allreduce(..., MPI_SUM)` calls so every rank receives the global
          centroid sums and updates the centroids identically.
      (d) We instrumented separate timers (`MPI_Wtime`) for Computation Time
          vs. `MPI_Allreduce` Communication Time.

STEP 3: Hybrid MPI + OpenMP Parallelization (`src/kmeans_omp.cpp`)
  - What we did:
    Combined distributed-memory MPI between processes (`P` ranks) with
    shared-memory OpenMP threads (`T` threads) inside each process.
    We also implemented and tested two major parallel design choices:
      (a) Accumulation Design Choice:
          - `atomic` mode: All OpenMP threads update a single shared centroid
            sum array using `#pragma omp atomic update`.
          - `private` mode: Each OpenMP thread accumulates into its own
            64-byte cache-line padded private array (`all_thread_sums`) with
            ZERO locks/atomics during the main loop, reducing once at the end
            of the iteration.
      (b) Loop Scheduling Choice:
          - Compared `schedule(static)`, `schedule(dynamic, 1024)`, and
            `schedule(guided)` using `#pragma omp for schedule(runtime)`.
      (c) OpenMP GPU Offload (`-g` flag):
          - Added `#pragma omp target teams distribute parallel for` so the
            same code can offload directly to NVIDIA GPUs on Vanda.

STEP 4: Hardware GPU Acceleration (`src/kmeans_metal_gpu.mm` & `src/kmeans_cuda.cu`)
  - What we did:
    Because the course rubric (Lecture 12 Slide 37) states: "If you choose
    X=OpenMP, then you also have to test on at least one GPU", we wrote:
      (a) `src/kmeans_cuda.cu`: Hybrid MPI + CUDA kernel for NUS Vanda's
          NVIDIA GPUs using on-chip `__shared__` memory centroid caching and
          block-level shared-memory reduction.
      (b) `src/kmeans_metal_gpu.mm`: Hybrid MPI + Apple Metal GPU compute
          shader for local Apple M5 GPU execution, using on-chip `threadgroup`
          shared memory (`s_centroids`) and zero-copy Unified Shared Memory.

KEY TIME DIFFERENCE TAKEAWAYS (CPU, MPI, AND OPENMP):
  1. Serial (1.3380 s) vs. Best Hybrid OpenMP (0.2500 s):
     - Exact Time Difference: Saved 1.0880 seconds (81.3% reduction in runtime),
       speeding up each iteration from 26.76 ms down to 5.00 ms (5.35x faster vs
       `kmeans_serial`, and 3.64x faster vs 1-thread `kmeans_omp`).
  2. Thread-Private Accumulators (0.2947 s) vs. Atomic Updates (1.8447 s):
     - Exact Time Difference: 1.5500 seconds difference!
     - Using `#pragma omp atomic` is 6.26x SLOWER than cache-padded thread-private
       accumulators because 4 threads fighting over the same 224 centroid memory
       locations 17.3 million times per iteration causes severe L1/L2 cache-line
       bouncing.
  3. Pure MPI (P=8, T=1) vs. Hybrid MPI+OpenMP (P=2, T=4 or P=1, T=8):
     - In Pure MPI at P=8 (`run_mpi_scaling.py`), `MPI_Allreduce` communication
       and barrier synchronization took 0.1442 s (32.8% of the 0.4403 s runtime).
     - Switching to Hybrid `P=2, T=4` cut `MPI_Allreduce` time down to 0.0096 s
       (saving 0.1346 s of communication overhead!), and `P=1, T=8` eliminated
       inter-rank MPI communication completely (0.0000 s), finishing in 0.2500 s.

4. HOW TO RUN ON NUS VANDA SUPERCOMPUTER (FROM THE NUS SHAREPOINT GUIDE & SLIDES)
--------------------------------------------------------------------------------
The SharePoint link you shared is the official NUS Research Computing Vanda User
Guide (referenced in Lecture 8 Slides 42-47 and Lecture 12 Slide 40). Here are
the exact commands to run this repository on Vanda:

1. Connect to NUS WiFi or NUS VPN, then SSH into Vanda:
     ssh <your_nusnet_id>@vanda.nus.edu.sg

2. Clone your GitHub repository onto Vanda and prepare the UCI HIGGS dataset:
     git clone https://github.com/Nithillen/dsa5208-project3-scalable-kmeans.git
     cd dsa5208-project3-scalable-kmeans
     python3 scripts/prepare_higgs_data.py

3. Start a 10-minute interactive compute node session to compile (never compile
   on the Vanda login VM!):
     qsub -I -l select=1:ncpus=1 -l walltime=00:10:00
     cd ~/dsa5208-project3-scalable-kmeans
     module load nvhpc-hpcx-cuda12/26.1
     make
     exit

4. Check your project ID / queue template if needed:
     hpc cpu
     hpc gpu
   (If your account uses a specific project code instead of `#PBS -P dsa5208`,
   update the `#PBS -P` line at the top of `scripts/vanda_mpi_256cores.pbs`
   and `scripts/vanda_hybrid_gpu.pbs`, or remove the `#PBS -P` line to use your
   default personal allocation.)

5. Submit the 256-Core Pure MPI job and the 72-Core Hybrid + NVIDIA GPU job:
     qsub scripts/vanda_mpi_256cores.pbs
     qsub scripts/vanda_hybrid_gpu.pbs

6. Monitor your jobs in the queue:
     qstat -u $USER
